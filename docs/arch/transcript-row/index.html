01范围

越界即作废。下面两栏是硬边界，不是倾向。

改什么

十个互不相干的排版结果给共同协议 MarkdownLayout；每个 layout 内部的排版算法一行不动
MarkdownBlockView + 11 子类收成一个 MarkdownLayoutView

行契约

跨 Model 与 View 的边界
TranscriptRowprotocol原 struct+enum
入
一个排版宽度。这一行的内容在行值构造时就已固定，之后不再变。
出
三样：① 这一行在该宽度下的完整排版结果；② 承载它的是哪一类视图；③ 把自己装进那个视图的动作。
答得出这三样的就是一种行。全架构的多态只发生在这一层，视图还不存在时就得答出高度，所以①是编译器不许碰 NSView 的。
TranscriptMarkdownLayoutRowprotocol新增
入
一个排版宽度。
出
一份 Markdown 排版结果，只此一样。上面那三样由它统一代答。
入会条件只有「交得出排版结果」一条。11 个文字行各写一行 conformance，高度、视图类、装配动作三个成员一行都不用写。调用方看不见这个协议。
TranscriptRowLayoutstruct原 RowMeasurement
入
这一行的内容，加一个排版宽度。两样缺一不可。
出
三样：① 这一行占的总高度，含上下留白；② 一份排好的、可以直接落笔绘制的排版结果（文字行有，卡片行没有）；③ 一套按字符查位置的服务：给坐标点还字符序号，给字符范围还矩形与文本。
三样是同一次排版的三种读法，宽度不变就不排第二次，谁也不能单独拿走。它还随身记着自己按哪个宽度排的，缓存认不认就看这一项。
TranscriptRowDelegateprotocol新增
入
行发来的两件事：「我把自己重建成了新值」（折叠切换、状态翻转），或「这件事我做不了，你来」（点在链接、复制、看全文、放大图上）。
出
无返回。宿主收下后自己决定接着做什么：换掉行值并处理高度变化，或执行那个意图。
今天这条从行往上的边根本不存在，两个宿主级意图在视图基类里直接被丢掉。新增一类上报只改这个协议和它的唯一实现方。

Markdown 组件

全案唯一改写组件公开契约处
MarkdownLayoutprotocol新增
入
一段内容加一个宽度，在各自的 make 里排一次版。
出
一份排版结果，对外只回答五件事：多高、按多宽排的、怎么画、第几个字在哪、哪块矩形可点。
五件事出自同一次 Core Text 输出，这是它们必须由一个协议一起给的原因。十个既有 XxxLayout 各加一行 conformance 就位，内部算法一行不动。
MarkdownLayoutViewclass原 BlockView
入
一份排版结果，加这一帧要涂色的若干字符段。
出
两样：画进居中列的像素（底板 → 色带 → 字形，顺序固定）；以及「刚才那一下点在哪个热区上」这条上报。
全仓唯一会画字的视图。它只认排版结果，不认行也不认表格，11 个按种类分的子类因此全部删除。文字光标形状逐行由排版结果自己决定。
TextGeometrystruct原 SelectionAdapter
入
一个坐标点、一个字符位置、或一对首尾位置。
出
对应的字符位置、该位置所在单元的范围、覆盖这段的矩形列表、这段的纯文本、词的边界，以及可供扫描的文本区段。
一台查询台，按能力命名而不是按用途命名：拖选、双击选词、三击选段、复制、将来的搜索读的都是它，加一个用途不用加成员。
TextHighlightstruct新增
入
一个字符范围，加一个已经定好的颜色。
出
视图照着填的一条带。数组顺序就是绘制顺序，后来的盖先来的。
颜色在选区那一侧就分档完了（窗口是否活跃、搜索命中是不是当前项），到视图手上只剩「这段填这个色」。搜索要的接口位就是这个类型，没有引入任何搜索机制。
TextRangestruct原 SelectionRange
入
一对首尾字符位置。
出
一段范围，可比较、可当字典键。
它只表示「从哪到哪」，语义由持有它的人给：同一个类型既当选区，也当搜索命中。
MarkdownHit / MarkdownHitActionstruct + enum改名
入
排版时算出的一块矩形，加这块矩形被点中意味着什么。
出
命中判定要的矩形，和点击后往上报的意图：开链接、复制、看全文、放大图 —— 四种，载荷各自完整，宿主不用回头反查。
每块热区恰好一个矩形，这是不变量，所以提成字段；「意味着什么」会随功能生长，所以收进 enum。意图里不带执行者，产出它的排版结果本来就跨线程可用。
BlockStyle.typesetWidth(forContainerWidth:)函数合并
入
容器宽度。
出
内容实际排版的宽度：去掉左右留白，再按上下限钳住。
全仓宽度只在这一个公式里换算。公式的三个输入都住在 BlockStyle 里，所以它跟着视觉设计走。TranscriptMetrics 整型并入删除，参数标签去掉宿主概念「row」。

Store 与 Controller

TranscriptStoreclass
入
一个会话 id（触发一次读盘）、一个排版宽度、以及被重建过的行值。
出
有几行、第 i 行是谁、某个 id 在第几行、某一行在某宽度下的排版结果，以及「哪些行在这个宽度下还没排过或已经过期」。

TranscriptViewControllerclasssplit
入
表格的三个提问（有几行、第 i 行多高、第 i 行拿什么视图）、尺寸变化、行发来的上报、选区提的行几何问题。
出
给表格的三个答案；一个全场唯一的排版宽度；resize 两段式的编排；选区要的行几何；以及交给上层的导航意图。
宽度是一个存储值，由滚动到底和表格尺寸变化两处维护，不再在每次问行高时去读表格的 bounds。66 行按种类分派视图的 switch 换成一个泛型挂载。

这是 VC 拆分的那一刀，切在「产品导航能力」这条独立的变更原因上：换成新窗口、换成 popover，只动协调器。

子视图 / 图层 / 动画：不需要任何新机制

SubviewPlan 在这个架构里不存在。 旧实现需要它（210 行 + 宿主侧 928 行）， 是因为只有一个通用 cell 类，排版结果必须给它发一张"要挂哪些子视图"的清单。 本架构里每一种卡片行都有自己的 view 类，直接 addSubview / addSublayer / addSymbolEffect —— 那是它自己的私事。

一条硬规则（诚实标注为代价）：参与跨行文本选区的文本，必须画进本行自己的 CGContext； 子视图 / 子图层里不得有参与跨行选区的文本。 推论必须被明确接受：「tool 卡片里的文本要能被跨行选中」= 这一行不能是卡片行，必须做成自绘行。

05高度契约

整条架构最硬的一条约束，也是四份提案冲突最激烈的裁决点。

每一行都必须能在自己的 view 不存在时、只凭 (自身载荷, 排版宽度) 算出一个 TranscriptRowLayout；这个函数是 nonisolated 的，所以 「高度路径不许碰 NSView」由编译器强制而不是靠纪律。

被否决的对手方案：离表 prototype 读 fittingSize

三条否决理由：(1) prototype 不在窗口里 ⇒ 拿不到 effectiveAppearance / backingScaleFactor ⇒ 高度与真实 view 分叉 ⇒ 行被裁切（原提案自认未解）； (2) 全量 tile 下 N 张卡 = N 次布局解算挤在一个 source phase（实测 10.7 ms / 301 行）； (3) 采纳它会把协议沿 actor 边界劈成两半。

C1 裁决的实测价值：把卡片行的高度查询压掉 60–100%

离表 prototype fittingSize（被否）106.8 µs10.7 ms + 冷建 2339 µs

A-6 不能假设 tile 全量 / 不全量缓存对两种调用量都是 O(1)/行，无预热假设

两条水平几何权威合并成一条

今天有两条必须"靠算术保持一致"的权威（VC 注释自承）：视图的 contentOrigin.x = (bounds.width - contentWidth)/2， 与选区的 rowRect.minX + TranscriptMetrics.contentX(...)。 审查中发现其中一份提案给出的合并公式（用 measuredWidth）是错的。 正确的统一是让选区原点用与视图完全相同的表达式、完全相同的输入： 

func contentOrigin(atRow row: Int) -> CGPoint {
    let rect = tableView.rect(ofRow: row)
    guard let item = store.row(at: row) else { return .zero }
    return CGPoint(
        x: rect.minX + (rect.width - layoutWidth) / 2,   // = 视图的 contentOrigin.x
        y: rect.minY + store.layout(for: item, width: layoutWidth).insets.top)
}

TranscriptMetrics.contentX / columnX 因此失去全部调用方 → 类型删除。两条权威变一条，不是"两次求值同一个式子"。

06缓存策略

一个字典，一行一条：[UUID: TranscriptRowLayout]。 宽度住在值里，无旁路字典。

缓存什么

insets + contentHeight + typesetWidth 一次 tile 要 301 行（或全表，不能假设）。重算成本动态范围 100×（10.8 µs ↔ 4180 µs）。必须 O(1)
markdownLayout（排版结果本体） 字符几何要它，而字符几何的访问模式是 O(拖选跨度)/tick + O(全表)/Cmd+A

不缓存什么

TextGeometry 实例构造实测 0.208 µs。存它 = 让每次 heightOfRow 给选区付钱；更重要的是：存它，缓存就知道了「选区」这个词
view / 位图AppKit 复用队列就是这个缓存
交互热区 · 选区状态 · hover · 复制文本现算 / 另有唯一真相 / 视图私有
行的 UI 状态（fold / status）不是缓存，是权威状态，住在行值里，是高度的输入
这一条正式否掉了我们讨论中「排版结果不必常驻」的判断。 内存侧证据强烈支持只存高度（0.5 MB/万行 vs 75–157 MB/万行）， 但选区的访问模式把排版结果钉回常驻：跨 500 行的一次 drag tick 若要重排 = 500 × 43.7 µs ≈ 21.9 ms，单 tick 超一帧预算 31%。

失效条件 · 只有三条

  1. 宽度不等 ⇒ miss ⇒ 现算覆盖（自愈，无显式驱逐）。判据 entry.typesetWidth == width 只在 store 里存在一份（今天有两份，一份 == 一份 !=）
  2. load(sessionId:) ⇒ 全清。今天这里是 11 行 removeAll()，漏一行就是脏缓存（🔴）；现在是一行
  3. replace(_:) ⇒ 丢该行一条。这是结构性的：换值就没缓存，没有"记得清"这件事

不加 LRU、不加容量上限 —— 一旦有上限，Cmd+A 就可能触发全表重排（10000 行 ≈ 438 ms）。

07enum 还是 protocol

判据不是"会不会生长"（那是预测，不可检验），而是五条可机械检查的问题。

判据内容
J1 穷举面积加一个成员时，已存在代码里必须新增一臂的地方数。≥2 ⇒ 必须 protocol；=0 ⇒ enum 无成本
J2 实现归属分支实现天然分散 ⇒ protocol；天然集中 ⇒ enum
J3 跨模块可扩展性存在模块外的实现者 ⇒ 只能 protocol
J4 空实现否决抽象逼出空壳 ⇒ 边界画错了，把这一类移出该抽象
J5 家族分层分支呈现子家族结构（default: 就是自供状）⇒ protocol（精化 + 默认实现）
被穷举分支的用 protocol；只被"解包"而从不穷举的可以留 enum； 不变量提字段、变量收 enum；跨模块有实现者的只能 protocol。

这条规则精确解释了同一份代码里的两个相反结论：RowLayout（10 方法 × 12 case）死了， LayoutPosition（5 case、零穷举）活得很好。

RowLayout 为什么不会重蹈

它的死因不止是 enum，还包括边界画错了 —— 一个类型同时承担了排版结果的共同类型、行的箱体几何、 热区词汇、字符几何、行的身份标签、以及一份值化的 view 树描述。

死因新架构为什么结构上不可能
(a) 穷举面积 = 10（406 行里方法体约 380 行） 成员实现体写在各 conformer 自己的文件里。加一种排版结果，MarkdownLayout.swift 改 0 行；加一种行，TranscriptRow.swift 改 0 行
正面回答攻击"protocol 只是把 120 个分支散成 41 个实现，总量没少"：J1 数的从来不是总量，是"加第 11 个时要碰几处旧代码"。enum=10 处，protocol=0 处。这个差不随规模缩小，只随规模放大。
(b) 家族分层被压平成 default:（三处，每一个都是未被表达的子家族） 协议的默认实现（"大多数不关心"）+ 第二个精化（"这是另一个家族"）
(c) 运行时 UI 状态被吸进排版结果（subviewPlan(origin:hoveredAction:selection:searchHighlights:flashingCopyIds:)） MarkdownLayout 的每一个成员签名都不接受运行时 UI 状态参数。想加一个 hover 参数就必须改一个组件级协议 —— 一次要过设计评审的可见改动
(d) 逼出空壳（LoadingPillLayout.draw {}） 卡片行根本不进这个抽象：它是 TranscriptRow 但不是 MarkdownLayout 的 conformer
(e) 身份成员 kindLabel新协议里没有对应物，也不许有
强制力必须诚实分档。 「一半由编译器守」是过度声称：CTLine 不 Sendable ⇒ 8/10 个 conformer 必须写 @unchecked Sendable，而 @unchecked 把检查整体关掉； 再叠加 SWIFT_VERSION = 5.0、未设 SWIFT_STRICT_CONCURRENCY、无 warnings-as-errors。 真正被编译器守住的只有「成员签名不含运行时 UI 状态参数」这一条，另一半靠 conformer 全 let + 一条 CI 源码检查。
