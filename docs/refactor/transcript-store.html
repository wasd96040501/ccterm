Transcript 重构方案 — 仅 history、session-agnostic

按 MVVM-C 规范重写 history transcript viewer。v5 塞进了自造的异步管道（Combine subject + 序列化 apply chain + row-count mirror + isReleased 保护标志），v10 把整条数据路径换成 VC 自己拥有的 for-await 循环 — 循环内 await 一个 off-main typeset，然后在同一个 MainActor tick 里 commit 行插入。无 mirror、无 chain、无 Combine、无 guard。

§ 0 · 唯一不变式

数据 mutation 和 tableView.insertRows 必须在同一个 MainActor tick 内落地。

如果这一条守住，v5 所有"辅助机制"都不需要存在：

  • 不需要 visibleBlocks mirror — mutation 和 insertRows 同 tick，dataSource 每次查询时 store.blocks.count 和 tableView.numberOfRows 天然一致。
  • 不需要 applyChain — for-await 循环体内 await Task.detached { ... }.value 返回到同一个 actor，一页 commit 完之前下一次 stream.next() 不会返回。
  • 不需要 Combine subject / .receive(on:) — 没有跨 tick 的 delta 需要传播，Store 不用发事件。
  • 不需要 isReleased 标志 — Task.cancel() 让下一次 try await 抛 CancellationError，循环自然退出。
违反这一条会让四个化简同时失效。v5 就是违反了它 — Store 在 events.send(...) 里同步 mutate blocks[]，VC 在 off-main typeset hop 回来后才 insertRows。为了补一致性窗口，v5 一次性招回 mirror + chain + subject + flag。之后每个 subsection 都会对着这条规则复核。

依赖方向自上而下（App → Store），事件方向自下而上（View → Controller）。Loader Task 挂在 Controller 上；Store 只是纯数据持有者，不拥有自己的 executor。

Phase 1 · 首屏同步（一次性）

左侧循环终止时（累积高度已 ≥ viewport 或到文件顶），右侧才 dataSource = self。这保证 § 2.19 attach 契约在最强形态下被满足 — 不是"tile 时懒 typeset"，而是"tile 时纯查表"。

Phase 2 · 后续异步 loader（循环）

for try await stream 自身 · ② checkpoint A（build 前） · ③ checkpoint B（commit 前） — prepareForRemoval 时 loaderTask.cancel() 即在下一个检查点抛 CancellationError 退出循环，无需 isReleased flag

左半是 MainActor 主线程工作（build），中间是 off-main（typeset），右半回到主线程（commit）。await 挂起循环 → 返回值到手 → commit 与 mutation 在同一 tick 完成 → 下一次 stream.next()。这正是 § 0 唯一不变式的运行形态。

宽度变化 · Live-resize + 编程式

攻击面：viewDidLayout 是所有宽度变化的最终汇聚点 — live-resize 拖拽、⌥⌘S 折叠 sidebar、split-view divider 编程式移动、全屏切换、窗口 setFrame 动画都会触发。方案按是否正在拖拽分流。

viewDidEndLiveResize 单独 override 一次 → 走 retileAtNewWidth（deferred 完整 retile）。这三层判断把"拖拽中每帧只失效可见行"（拖拽性能）和"最终宽度落定后完整 retile"（缓存正确性）解耦，同时覆盖所有非拖拽的宽度变化路径（sidebar / split / full-screen）。

Attach 契约 — § 2.19 合规

每个可见 block 只在 一个 宽度下 typeset。数据在 dataSource = self 绑定 之前 已经落到 store.blocks，所以第一次 heightOfRow 查询就发生在已稳定的表宽下。

首帧预算 · 按 viewport 高度停止

典型场景（1 页填满）

约 20–50 ms — 一次 file read + 只 typeset 需要的行数（约 15–20 个 block）。零白屏。

工具消息密集

约 40–80 ms — 走 2–3 页找到足够的可见高度。全部 typeset 都是 warm cache。

超高单条消息

约 10–30 ms — 一条 500 行 fileEdit diff 就超过 viewport，只 typeset 一个 block 就停止。比典型场景还快。

病态场景（接受）

整个文件是一个未闭合的 group run — 同步走到文件顶。10 MB 文件可能卡秒级。不加兜底：bail-out 也是让用户等，还先看到空白，不如一次到位。
