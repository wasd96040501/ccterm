# Transcript tab

A session's tab — a New tab before its first prompt, the transcript and the composer after — and the documents it opens beside itself. The design is `design/transcript/` (README + 01–08, and `preview.js` / `preview.css` / `preview-live.js` / `preview-live.css` for exact values); build to it one to one.

## Layers

```
Page/        model — messages → TranscriptPage (entries, runs, documents), and the mapping from AgentSDK/Sessions types to display values (`Approval+Call`, `Question+Call`, `Plan+Call`, `TaskNews+Report`, `PromptImage+Block`, `SessionDivider+Page`, `TaskListItem+Task`, `Tile+Page`). No AppKit. The values a row draws (`WorkLine`, `Caption`, `Note`, `SessionDivider`, `Approval`, `Question`, `Plan`, …) are `DisplayModels`' (`DisplayModels/Transcript/`); the entries that hold calls, reports and the page itself stay here.
Rows/        a page's entries → PageRow (pure), and `PageRow+View`, the one switch to the row views (`Components/Rows/`).
Documents/   what opens beside: DocumentViewController (the shell), the markdown body (TranscriptKit's), and the mapping from calls to display values (`DocumentHeader(_:)`, `CommandSummary+Call`, `SourceLines+Call`, `DocumentMarkdown`). The bars and the command, source and image bodies are `Components/Documents/`.
Composer/    ComposerModel (pure: the session's facts worded into a `ComposerPresentation` — every chip, menu, status; an item's id back to its `SessionSettings.Change`). The card is `Components/Composer/`.
NewSession/  NewSessionDraft + NewSessionModel + BranchPickerModel/BranchRules (pure), NewSessionMenu (the branch menu's `MenuContent`) and `NewSessionContent+Model`. The New view is `Components/NewSession/`.
TranscriptViewController   the transcript: page, disclosure, selection, reveal — shown the states it is handed.
SessionTabViewController   a session's tab (or New tab), the binder of the New view and the composer (one instance, which moves): the one subscription to the session.
TranscriptTab              the feature's door: a tab's identity, its `Context`, and the one place its tabs are built.
```

Dependencies point down only, and siblings don't know each other. `Page/` reads `AgentSDK`, `DisplayModels` and the value types of `ccterm/Sessions/` (`LocalPrompt`, `SessionState.Restart`, `SessionFailure`); a display value stores no AgentSDK type and arrives worded — its words are composed in `Page/`'s `+Call` / `+Page` extensions — and the entry that needs the call beside it (`TranscriptEntry.question` / `.plan`, `NewsRun.reports`) keeps it. `Rows/` reads `Page/` and the row views. `Composer/` and `NewSession/` read the value types of `ccterm/Sessions/`, `ccterm/Accounts/` (`ModelCatalog`) and `ccterm/Git/` (`RepositoryState`, `Checkout`) and build display values — never a store. `Documents/` reads `Page/` and AgentSDK's tool types, and only there a call is read; it never names the root or a store: what it needs from outside (`load`, `makeConversation`, `showInTranscript`, `decide`) arrives as closures. The root (`TranscriptTab`, the session tab, the transcript) reads the rest, and the stores through `TranscriptTab.Context` — `SessionStore` (`ccterm/Sessions/`) is the one way to a session, read and talk. `MainSplitViewController` is the coordinator and decides **placement only** — which editor a tab opens in, what is focused, what the window shows. The feature builds its tabs: the app names only `TranscriptTab` and `TranscriptTabDelegate` from it, and hands it a `TranscriptTab.Context` (`TranscriptTab.makeItem` wires a subagent's conversation, the document's `makeConversation`, as a `TranscriptViewController` following its own file, with the same delegate and store and no composer).

## Rules

- **Every pop-up is `MenuPanel`.** Model, Effort, Mode, the folder and the branch draw the design's rows (`.lv-menu`): the owner builds a `MenuContent` from its model (`NewSessionMenu` for the branch; the composer's and the New view's folder menu are built inside the package from the value they are shown) and applies what is chosen. What opens follows the design's tree: a menu (Effort, Mode, the folder) is a real `NSMenu` — the system's tracking, keys and chrome; a panel (the branch's filter, the model list's sticky heads, its 360-pt scroll and Fast Mode under it, which no `NSMenu` has) is the package's panel. Never an `NSMenu` or `NSPopover` built beside `MenuPanel`, so every pop-up keeps the one set of rows.
- **Words are decided in `Page/`** — and a document's in `DocumentHeader`, `CommandSummary`, `SourceLines` (their `+Call` / `+Document` extensions in `Documents/`) and `DocumentMarkdown`. Every sentence, label and stat is built there, localized, as `StyledText` (words plus the distinctions a view draws: noun, code, added, removed, failure). A view picks fonts and colours for those styles; it never composes wording or formats a number. Tests assert on the words without AppKit. A view keeps only fixed control copy (*Allow*, *Deny*, *Submit*, *Show N more*, *Interrupted*, *Summary*); a sentence, a stat, a date or anything read out of a call's input is the page's (`Approval`, `Question.Item`, `LocalCommand.title`, `SessionDivider.label`, …).
- **Row views are drawn from page values, never from the SDK** — they don't import `AgentSDK`. A document body is drawn from a display value too: the app's mapping (`CommandSummary(call)`, `SourceLines.change(calls)`) reads the call's typed input and output (`use.input(as:)`, `result?.toolOutcome(_:)`) — mirroring every tool in `Page/` would buy nothing — and the header and stats are worded in `DocumentHeader`.
- **`Page/` types are `nonisolated`** (the app defaults to `MainActor`); pages are built off the main actor.
- **TranscriptKit draws what it can.** Replies, prompts and commands (a command, a `!` command or a pasted picture is the user's bubble with a *token*: `Bubble` in `Page/`, `TranscriptRowContent.UserMessage` where a row meets TranscriptKit), another agent's words (a blockquote), a plan, and every markdown document are TranscriptKit `.markdown` / `.userMessage` rows or a `TranscriptView` — no second renderer. Only work lines, captions, the note under a bubble (`NoteRowView`: a command's output, a prompt's delivery), thumbnails (`AttachmentsRowView`), dividers, questions and approval controls are `.view` rows.
- **A prompt written here is an entry from Send.** `TranscriptPage.init(_:prompts:restarts:)` draws each `LocalPrompt` at the end under its uuid, which is the id the transcript's own message takes (a message with a uuid is an entry under it), so the CLI's replay confirms it in the same rows; its delivery is the `Note` under it. A prompt handed back to the field is not drawn. Withdraw and Resend go to the store from `TranscriptViewController`.
- **One row per line.** A run's line, each item, *Show N more* and the approval card are separate rows (`PageRow.Part`); expanding is inserting rows: one batch anchored on the run's line (`.row(first)`, or the clicked row for *all*), with `.effectGap`, so the line holds still and the rows below slide.
- **A row that changes its place slides.** `PageRow.changes` names such a row (a queued prompt the CLI takes into the running turn) in `moved`, announced with `moveRow(at:to:)` between the removals and the inserts, so its view travels and the rows between make way; it is never removed and inserted again.
- **A row's box is its content; the gap above it is the list's.** A row view pads nothing above or below itself — except a line of work, whose box is its hover (28 pt at both levels, the words `WorkLineRowView.air` in from top and bottom), so the hover and the click reach the same box; that air is part of the gap. Two levels (design README "Spacing"): the transcript's gap between entries, less a line of work's air on either side, and `PageRow.spacingAbove(after:)` for what a line discloses (0) and the approval card (6), answered through `customSpacingAboveRow`. A disclosed row carries its own gap, and every row a run ends on has the same air, so opening and closing notes nothing; a prepended chunk notes the row it lands above.
- **Row views keep `PageRowView`:** `static height(for:width:)` from the model alone, idempotent `configure(with:)`, events up through `PageRowViewDelegate` by id. `PageRow+View` is the one switch from row kinds to views. The row views and `PageRowView` live in `Components` (`Rows/`); `PageRowViewContractTests` there holds every row view to it, on literal display values — laid out at the height it declares, nothing outside or cut, nothing moved by reconfiguring, selecting or flashing; a new row view adds its fixtures there.
- **A row acts on press; a press that opens a document gives it the focus.** Handle the click in `mouseDown` (clickCount 2 is a double-click → `pinned`). A press that opens a document stops there: the coordinator hands the focus to the document's tab, so ⌘W closes what was just opened. Any other press calls `super.mouseDown(with:)`, which reaches the transcript and makes it first responder. Controls inside a row (a link, the chevron, a button) handle their own tracking.
- **A tab follows its session once; it never asks whether it is live.** `SessionStore.states(at:)` gives a session at rest (one value) or live (every change, newest only). The session tab is its only subscriber: it hands each state to the transcript (`show(_:)`) and, worded by `ComposerModel` as a `ComposerPresentation`, to the composer, so the two never disagree. The transcript turns each into a page off the main actor; the first page is shown as a reader's load (last screen, then history in chunks); later ones are applied as `PageRow.changes` in one batch; while a page is being shown only the newest state waits.
- **Settings rules live in `ccterm/Sessions/`, words in the models.** What a change brings with it and when it lands (`SessionSettings.applying`, `SessionState.timing(of:)`) is decided there, for a draft and a live session alike; `ComposerModel` and `NewSessionModel` only word the answers, localized, and are tested without AppKit, as `Page/` is.
- **Live states come from the session's state, not from the file.** The builder yields settled states, plus `running` for the calls of the last assistant turn; over a live state it adds `.waiting` for a call with a pending request, `.preparing` for a streaming call, and the streaming reply under the id its finished block will get. Answers (`pageRowView(_:didDecide:forCall:)`, `approvalBarView(_:didDecide:forCall:)`) become a `PermissionDecision` in `Page/` (`Decision.permissionDecision(for:)`) and go to `SessionStore.respond(toCall:at:with:)`.
- **A document is a shell and a body.** `DocumentViewController` loads the `Document` when it first appears and follows it while its call is still going (`Document.isLive`), words the jump bar (`DocumentHeader`), shows an approval bar while the call waits, and embeds the body it picks itself (`makeBody(for:)`, the one place a call meets a body: it builds each body's display value, and the subagent conversation). It stays here because it reads `Document`, which holds calls. It has no delegate and names no root type; *Show in Transcript* is a closure it is given. A body is an `NSViewController`: command, source (change / new file / read) and image from the Components package, markdown, or — for a subagent whose conversation is on disk — a `TranscriptViewController` on `subagents/agent-<id>.jsonl`.
- **A tab's identifier is a `TranscriptTab`** — `.newSession(UUID)`, `.transcript(URL)` or `.document(DocumentReference)` (transcript URL + id) — so history rebuilds it (never a New tab: its draft is gone) (`editorArea(_:tabViewItemWithIdentifier:)`, decoded with `TranscriptTab(identifier:)`) and a second open finds it. A tab asks its host through `TranscriptTabDelegate`: *open* hands over an identity and a `makeItem` the host calls only if no such tab is open; *reveal* selects the transcript's tab and shows an item in it.

## Adding a tool

- **A tool of an existing kind** is one line in `ToolKind.init(_:result:)`. Its row reads the kind's input keys (`command`, `file_path`, `pattern`, `url`, `query`, `description`) and its meta falls back to nothing, so it reads right before it gets words of its own; give it those in its kind's branches of `WorkLineWriter` when it needs them. `WorkLineWriter` is used only inside `Page/`; a document's header and body reach for the small Page values it shares (`Tile(calls:)`, `ToolCall.toolName`, `TimeInterval.durationText`, `String.firstLine`) instead.
- **A new kind** is a design change (the kinds are the design's closed vocabulary, README "Kinds"). Add the `ToolKind` case and follow the compiler: every place that gives a kind its words, tile or document switches over it exhaustively — no `default:` there.
- No registry or per-tool protocol: tools are added far more often than kinds, and a tool is one line.

## Reuse before adding

| Need | Use |
|---|---|
| A kind's tile, any state | `TileView` |
| `StyledText` on screen | `attributedString(font:color:)`; `NSColor.addedText` / `.failureText` |
| A button (Allow, Deny, Submit, Approve, Open…) | `PillButton` — the design's `.btn`, with its `kbd` hint |
| A line of work (run, item, news) | `WorkLineRowView` |
| Another agent's or a plan's words | `.markdown` row (`PageRow.quoted` for another agent's) |
| A document of words | `MarkdownDocumentViewController` + `DocumentMarkdown` |
| Numbered monospaced lines | `NumberedLinesView` (Components, behind the command and source bodies) |
| A subagent's conversation | `TranscriptViewController` |
| The sidebar's party glyphs and coral | `.sidebarAgent`, `.sidebarSession`, `.sidebarWorkflow`, `.sidebarCoral` |
